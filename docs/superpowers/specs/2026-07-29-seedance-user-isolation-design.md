# Seedance 视频记录用户隔离设计

日期：2026-07-29  
项目：Davis-Design-Management-Center  
状态：已确认，待实施

## 目标

Davis Video / Seedance 页面按 Supabase 登录用户隔离项目和生成记录：

- 普通用户只能查看、创建、修改、重新生成和删除自己的内容。
- `davidxxu@webank.com` 与 `judyzzhang@webank.com` 可以查看所有用户的项目及生成记录。
- 两位超级管理员查看他人项目时为只读，不能编辑、重新生成、覆盖保存或删除。
- 超级管理员仍可正常操作自己创建的项目。

## 现状

六张视频业务表都已有 `owner_id uuid`：

- `video_projects`
- `video_assets`
- `video_segments`
- `video_tasks`
- `video_outputs`
- `video_operation_logs`

当前六张表均使用单一 `ALL` RLS 策略：`owner_id = auth.uid()`。这已经保护普通用户数据，但没有超级管理员跨用户只读能力。

前端 `seedance/app.js` 的云端恢复和任务查询也普遍显式添加 `.eq('owner_id', state.user.id)`，因此即使数据库开放管理员读取，前端仍不会展示其他人的记录。

## 方案比较

### 方案一：仅修改前端过滤

优点是改动少。缺点是权限可被绕过，不能作为数据安全边界，因此不采用。

### 方案二：RLS 强制权限并配合前端只读状态

数据库负责最终授权，前端负责正确展示和禁用操作。普通用户保持原行为，管理员获得跨用户只读能力。此方案改动集中、可验证、无需新增服务，采用此方案。

### 方案三：新增管理员 Edge Function 聚合接口

可以集中返回管理员数据，但会增加函数维护、分页协议与失败链路；现有表结构和 RLS 已足够完成目标，因此暂不采用。

## 数据库设计

为每张视频业务表拆分策略：

1. `SELECT`
   - `owner_id = auth.uid()`，或
   - 当前 JWT 邮箱属于 `davidxxu@webank.com`、`judyzzhang@webank.com`。
2. `INSERT`
   - 仅允许 `owner_id = auth.uid()`。
3. `UPDATE`
   - `USING owner_id = auth.uid()`；
   - `WITH CHECK owner_id = auth.uid()`，禁止转移所有者。
4. `DELETE`
   - 仅允许 `owner_id = auth.uid()`。

管理员例外只存在于 `SELECT`，不扩展到任何写操作。身份判断使用 Supabase Auth JWT 邮箱，不信任前端 localStorage 中的用户名或角色。

策略应用于六张视频业务表。现有 `ALL` owner policy 将被替换，避免宽泛策略与新策略叠加造成误授权。

## 前端设计

在 `seedance/app.js` 中增加统一身份与权限判断：

- `isVideoSuperAdmin(user)`：根据当前 Supabase Auth 用户邮箱判断是否为两位管理员。
- `isForeignVideoProject(project)`：项目 `owner_id` 与当前用户 ID 不一致。
- 普通用户的项目、片段、任务、输出查询继续限定自己的 `owner_id`。
- 管理员的读取查询不增加 owner 过滤，并保留各记录的 `owner_id`。
- 管理员加载他人项目时，将当前工作区标记为只读。
- 对他人项目禁止所有会产生写入的入口，包括生成、重新提交、重新编辑、删除、合并写回、上传素材和项目保存。
- 前端禁用只是用户体验保护；即使遗漏入口，数据库 RLS 仍会拒绝写入。
- 管理员自己的项目不进入只读状态，现有功能不受影响。

不改变普通用户的页面布局和工作流程，不修改 Seedance、Ark 或 Google Drive 生成链路。

## 数据流

普通用户：

登录 → 查询自己的 `video_projects` → 按项目读取自己的片段、任务和输出 → 正常生成与管理。

超级管理员查看自己：

登录 → 查询全部项目 → 选择自己项目 → 正常读写。

超级管理员查看他人：

登录 → 查询全部项目 → 选择他人项目 → 加载片段、任务和输出 → 标记只读 → 禁止所有写操作。

## 错误处理

- 无有效 Supabase Auth 会话时，不加载视频数据并沿用现有登录处理。
- 管理员身份无法确认时按普通用户处理，默认最小权限。
- 对他人项目的写操作在前端给出只读提示，不发送数据库或 Ark 请求。
- 数据库拒绝写入时记录明确错误，不把失败任务误标记为已提交。

## 测试与验收

### 数据库权限

使用三类身份验证六张表：

1. 普通用户 A 能读取和写入自己的记录。
2. 普通用户 A 不能读取、修改或删除用户 B 的记录。
3. `davidxxu` 与 `judyzzhang` 能读取用户 B 的记录。
4. 两位管理员不能修改、删除或向用户 B 项目插入从属记录。
5. 两位管理员能正常读写自己的记录。

### 前端行为

1. 普通用户项目列表与生成记录中不出现其他用户内容。
2. 管理员能看到全部云端项目和对应生成输出。
3. 管理员选择他人项目后，生成、编辑、重试和删除入口不可执行。
4. 管理员选择自己的项目后，功能保持正常。
5. 页面刷新、项目切换和云端草稿恢复后，只读状态仍正确。

### 回归

- Seedance 创建任务、轮询、Google Drive 同步和视频播放链路不变。
- 版本项目 V-2、V-3 自动创建逻辑不变。
- 普通用户现有本地草稿不会被其他用户的云端项目污染。

## 发布顺序

2. 再提交并发布 `seedance/app.js` 的管理员读取与只读保护。
3. 使用普通用户、`davidxxu`、`judyzzhang` 三类会话验收。
4. 检查 Supabase 日志，确认没有跨所有者写入成功。
