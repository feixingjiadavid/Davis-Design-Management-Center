# Davis Video Studio：成片单元与批量生成架构设计

日期：2026-08-11
状态：已确认方案 A，待用户审核书面规格后进入实施计划

## 1. 目标

在不恢复剪映 Bridge、不把 Davis Video Studio 做成剪辑器的前提下，把现有“一级项目 → 子生成任务”升级为适合真实活动视频生产的结构：

```text
一级业务项目
  ↓
成片单元 / 交付模块
  ↓
具体生成子任务
  ↓
Seedance 生成任务 / 输出
```

典型例子：

```text
周年活动
├─ 互动暖场视频
│  ├─ 张三｜5周年｜第1次生成
│  ├─ 李四｜5周年｜第1次生成
│  ├─ 王五｜10周年｜第1次生成
│  └─ 张三｜5周年｜第2次生成（用户主动重生成）
├─ 开场视频
│  ├─ 主视觉开场动画
│  └─ 主视觉结尾动画
└─ 采访包装视频
   ├─ 片头包装
   ├─ lower third 包装
   └─ 转场包装
```

核心目标：让一个真实业务项目可以容纳多个成片单元，每个成片单元下可以有几十甚至上百个独立生成子任务，并且支持批量创建、批量审核和严格的费用确认。

## 2. 硬性产品原则

### 2.1 任何新增模型费用都必须人工确认

AI、系统、质检模块可以分析、排序、提示、建议，但不得自动触发新的 Seedance 生成。

以下行为都必须由用户主动确认后才可真正提交 Ark：

- 首次单条生成；
- 首次批量生成；
- 单条重新生成；
- 批量重新生成；
- 任何会产生新的 `video_tasks` / Ark 推理费用的操作。

确认界面必须在提交前展示人民币预计费用。

### 2.2 自动重试只允许用于“明确未产生模型费用”的技术失败

可以自动重试的范围仅限于明确没有创建有效 Ark 推理任务、没有产生 usage 的技术失败，例如提交前网络故障、服务端瞬时 5xx 等。

以下情况不得自动重试：

- 已收到 Ark provider task id；
- 已产生 usage；
- 内容质量不理想；
- 人脸、动作、手部、构图、尾帧一致性等内容问题。

内容质量问题只允许标记为“建议检查 / 建议重新生成”，最终由用户决定。

### 2.3 创建子任务不等于立即付费生成

批量导入或批量创建只建立“草稿生成任务”，不自动提交 Ark。用户可以先检查名称、图片、Prompt、模式、模型、分辨率、时长和费用，再选择部分或全部提交。

## 3. 数据模型

### 3.1 保留现有表含义

现有核心表继续保留：

- `video_project_groups`：一级业务项目，例如“2026 周年活动”；
- `video_projects`：一次具体的独立生成子任务；
- `video_segments`：子任务内部片段；
- `video_tasks`：真实 Ark 生成任务；
- `video_outputs`：生成输出。

现有 owner/RLS、项目类别、费用统计、回调/Worker、Google Drive 链路保持不变。

### 3.2 新增 `video_deliverables`

新增一张中间层表，代表“成片单元 / 交付模块”。

建议字段：

```text
video_deliverables
- id uuid primary key
- owner_id uuid not null
- parent_group_id uuid not null
- name text not null
- deliverable_type text null
- description text null
- sort_order integer not null default 0
- status text not null default 'active'
- metadata jsonb not null default '{}'
- created_at timestamptz not null
- updated_at timestamptz not null
```

约束：

- `parent_group_id` 指向 `video_project_groups.id`；
- owner 必须与父项目一致；
- 软删除，不物理删除历史生成结果；
- 同一一级项目内 `sort_order` 决定显示顺序。

### 3.3 扩展 `video_projects`

给具体生成子任务增加以下字段：

```text
- deliverable_id uuid null
- subject_key text null
- attempt_no integer not null default 1
- retry_of_project_id uuid null
- review_status text not null default 'draft'
```

字段语义：

- `deliverable_id`：归属的成片单元；
- `subject_key`：同一业务对象的稳定标识，例如员工工号或 `zhangsan_5y`；
- `attempt_no`：同一 `subject_key` 下第几次生成尝试；
- `retry_of_project_id`：若为用户主动重生成，指向上一条生成子任务；
- `review_status`：`draft / pending_review / accepted / backup / rejected / needs_retry`。

兼容规则：

- 历史 `video_projects.deliverable_id` 允许为空；
- 历史任务继续正常显示在父项目下的“未归类”区，不强制迁移；
- 不修改现有 `version_root_id / version_number / version_source_project_id` 的既有语义，避免与历史版本逻辑冲突。

## 4. 页面信息架构

### 4.1 左侧树

从当前：

```text
一级项目
  └─ 子任务
```

升级为：

```text
一级项目
  ├─ 成片单元 A
  │   ├─ 子任务 1
  │   ├─ 子任务 2
  │   └─ 子任务 3
  ├─ 成片单元 B
  │   └─ 子任务 4
  └─ 未归类
      └─ 历史子任务
```

交互继续遵守 R50 原则：

- 选中状态与展开/收起状态完全独立；
- 点击箭头只负责展开/收起；
- 点击项目/成片单元/子任务只改变 selection；
- 当前正在使用的节点也允许收起。

### 4.2 一级项目视图

选中一级项目时展示：

- 项目名称、项目类别；
- 成片单元列表；
- 每个成片单元的任务数、已生成数、待审核数、通过数；
- 项目累计已产生费用；
- 新建成片单元按钮；
- 批量导入入口。

不在一级项目页塞入具体 Seedance 参数。

### 4.3 成片单元视图

选中成片单元时展示：

- 单元名称与说明；
- 任务总数；
- `draft / generating / pending_review / accepted / rejected / needs_retry` 汇总；
- 批量创建/导入任务；
- 批量选择；
- 批量提交生成；
- 批量标记审核状态；
- 仅由用户主动触发的批量重新生成。

### 4.4 子任务视图

保留现有首尾帧 / Storyboard / 纯文字三种生成工作区。

新增信息：

- 所属一级项目；
- 所属成片单元；
- `subject_key`；
- 当前是第几次生成尝试；
- 若为重生成，显示来源任务；
- 当前审核状态。

## 5. 批量任务创建

### 5.1 第一版输入方式

第一版支持 CSV/Excel 导入，面向类似“45 位员工暖场互动视频”的场景。

导入后先进入预览，不直接写 Ark。

建议最小字段：

```text
任务名称
subject_key
历史照片
当前照片
生成模式
Prompt/动作模板
模型
时长
分辨率
比例
```

文件素材字段可以先支持“文件名匹配”，即用户批量上传图片后，表格用文件名对应；若找不到文件，任务进入“素材缺失”状态，不允许付费提交。

### 5.2 批量创建结果

确认导入后：

- 在指定成片单元下创建 N 个 `video_projects` 草稿；
- 每个项目写入 `subject_key`；
- 首次创建时 `attempt_no = 1`；
- 不创建真实 `video_tasks`；
- 不调用 Ark；
- 不计入“已产生费用”。

## 6. 生成与费用确认

### 6.1 单条首次生成

点击生成后先展示：

```text
任务名称
模型
时长
分辨率
预计人民币费用
```

确认按钮直接带费用，例如：

```text
确认生成 · ¥3.82
```

只有用户点击后才真正提交。

### 6.2 批量首次生成

用户可以勾选多个草稿任务。

确认弹窗必须展示：

- 本次任务数量；
- 每条预计费用；
- 预计总费用；
- 当前项目已产生费用；
- 生成后项目预计累计费用。

只有点击“确认生成 N 项 · ¥X.XX”后才逐条/分批提交。

### 6.3 单条重生成

重生成不覆盖原任务，创建一个新的 `video_projects`：

- `subject_key` 与原任务一致；
- `attempt_no = max + 1`；
- `retry_of_project_id = 原任务.id`；
- 默认复制原任务模式、素材和参数，允许用户在提交前修改；
- 仍然必须单独确认预计费用。

### 6.4 批量重生成

用户先人工勾选需要重做的对象，再打开费用确认。

禁止：

- AI 自动勾选后直接提交；
- 根据质检结果自动批量生成；
- 后台定时自动重生成。

## 7. 审核状态

生成成功后默认：

```text
pending_review
```

用户可以标记：

- `accepted`：通过/采用；
- `backup`：备用；
- `rejected`：废弃；
- `needs_retry`：用户认为需要重新生成，但此状态本身不触发费用。

`needs_retry` 只代表人工判断结果。用户还需再次点击“重新生成”并确认费用，才会创建新的付费任务。

## 8. 项目与成片单元进度

统计只读取已有数据，不自动触发生成。

成片单元至少展示：

```text
任务总数
草稿数
生成中
待审核
已通过
备用
需重做
失败
累计已产生费用
```

一级项目展示所有成片单元汇总。

费用仍以真实 Ark usage 为“已产生费用”的优先来源，前端估算只能用于“预计费用”。

## 9. 权限与删除

沿用当前 owner/RLS/read-only/super admin 行为。

删除规则：

- 删除一级项目：软删除父项目、其成片单元和其下子任务；历史 Ark 任务、Google Drive 输出不物理删除；
- 删除成片单元：软删除该单元及其子任务，不删除一级项目；
- 删除子任务：只软删除该子任务；
- 已有费用、usage 和历史输出必须继续可审计。

## 10. 错误处理

### 10.1 批量导入错误

导入预览必须逐行显示问题，例如：

- 素材文件未匹配；
- 任务名称为空；
- 模型无效；
- 时长不合法；
- 重复 `subject_key` 但用户未指定为新尝试。

有错误的行不能提交；其他合法行可继续。

### 10.2 生成提交错误

批量提交时每条任务独立记录状态。

某一条失败不能导致已经成功提交的其他任务回滚，也不能自动重复扣费。

### 10.3 费用不确定

若预计费用无法可靠计算，则该任务不得使用“确认生成”主按钮，必须显示“费用暂不可计算”，直到参数或价格数据完整。

## 11. 第一阶段范围

本阶段只实现：

1. `video_deliverables` 成片单元层；
2. `video_projects` 新增归属、subject、attempt、retry、review 字段；
3. 项目 → 成片单元 → 子任务三级树；
4. 成片单元创建/删除/排序；
5. CSV/Excel 批量创建草稿子任务；
6. 单条和批量付费生成前的费用确认；
7. 人工审核状态；
8. 用户主动单条/批量重生成关系链；
9. 历史 R50/R53 数据兼容。

本阶段明确不做：

- 剪映 Bridge；
- 时间线剪辑；
- 自动质检触发重生成；
- AI 自动花钱；
- 自动素材缺口补生成；
- 项目交付包；
- 完整素材墙；
- 与 Premiere/AE/达芬奇集成。

## 12. 测试与验收

### 12.1 数据层

必须验证：

- 历史没有 deliverable 的任务仍可打开；
- 新建成片单元 owner 与父项目一致；
- 子任务不能挂到别人的成片单元；
- 删除单元不会物理删除历史费用与输出；
- `attempt_no` 与 `retry_of_project_id` 关系正确。

### 12.2 UI

必须验证：

- 项目、成片单元、子任务各自可以选中；
- selection 不强制展开；
- 45+ 子任务时左侧树仍可用；
- 历史未归类任务仍然可进入原工作区；
- 首尾帧 / Storyboard / 纯文字原功能不回归。

### 12.3 费用安全

必须验证：

- 批量导入不会调用 Ark；
- 创建草稿不会产生 `video_tasks`；
- 没有人工确认不能提交付费请求；
- `needs_retry` 不会自动提交；
- 重生成确认前展示新增费用和累计费用；
- 批量提交部分失败时不自动重复提交已经成功的项；
- 已产生费用继续以真实 usage 为准。

### 12.4 周年活动验收场景

以如下真实场景作为第一阶段验收：

```text
周年活动
└─ 互动暖场视频
   ├─ 25 位 5 周年员工
   └─ 20 位 10 周年员工
```

用户可以一次导入 45 条草稿任务，检查后选择 45 条首次生成，在看到预计总费用后明确确认；生成完成后人工审核，其中若有 5 条需要重做，用户将这 5 条标记为 `needs_retry`，再主动选择重生成、看到新增预计总费用并确认，系统创建 5 条新的生成子任务，而不是覆盖原来的 5 条。

最终树中允许出现 50+ 个子任务，并且每条任务仍能追溯到所属员工、生成尝试次数和上一条任务。

## 13. 迁移原则

- 所有数据库变更使用可回滚 migration；
- 新字段先允许兼容旧数据；
- 不重写现有 R50/R53 已验证的核心生成 runtime；
- `seedance/app-v46.js` 和 `seedance/ffmpeg-class-worker.js` 非必要不动；
- 优先在 `ai-assistant.html`、`seedance/app.js`、数据库 migration/RPC 范围内实施；
- 任何会改变现有费用统计口径的改动必须单独验证。
